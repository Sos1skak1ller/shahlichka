Задание на реализацию отдельного пакета `recsys/`. Пакет самостоятельный: **не импортирует `gaming_engine`**, не знает про промо, бюджет и уровни аватара. Engine потребляет его через 3 функции.

## 0. Среда исполнения

Обучение и инференс происходят **локально на MacBook Pro 16" (M5, 32 ГБ unified memory, 1 ТБ SSD)**. Машина мощная, поэтому большинство типичных для ноутбука ограничений здесь не действуют — но есть два места, где ошибка обходится дорого независимо от железа: работа с памятью при чтении датасета и детерминизм. Их читать обязательно.

| Параметр | Значение | Что из этого следует |
|---|---|---|
| CPU | Apple M5-серии (в 16" — Pro/Max), ARM64 | нативные arm64-колёса numpy/scipy/pandas, Rosetta не нужен |

### Память: главная ловушка

32 ГБ — это много, но потратить их можно за одну строчку. `purchases.csv` — 45,8 млн строк. Если прочитать его наивно, идентификаторы приедут как Python-строки (`object` dtype), и фрейм займёт **15–25 ГБ** — машина уйдёт в своп и всё встанет. Тот же самый файл, прочитанный с явными типами и сразу переведённый в целочисленные коды, занимает **меньше 1 ГБ**.

Разница здесь не в железе, а в трёх строчках кода:

```python
# правильно: только нужные колонки, сразу коды вместо строк
usecols = ["client_id", "transaction_id", "product_id",
           "transaction_datetime", "trn_sum_from_iss"]
df = pd.read_csv(path, usecols=usecols, engine="pyarrow")
for col in ("client_id", "transaction_id", "product_id"):
    df[col] = df[col].astype("category").cat.codes.astype("int32")
```

При таком чтении можно грузить датасет целиком, без чанков — это проще и быстрее, чем почанковая сборка CSR. Чанковый путь из §2 остаётся в коде как опция (`--chunksize`) на случай, если кто-то из команды работает на машине с 16 ГБ, но дефолтный путь на этой машине — чтение целиком.

Бюджет по памяти на полном прогоне: фрейм < 1 ГБ, CSR товарной матрицы ~340 МБ, факторы и временные массивы — единицы мегабайт. Итого около 2 ГБ из 32. Запас позволяет держать открытыми IDE, `npm run dev` и обучение одновременно.

### Параллелизм: можно, и он не ломает детерминизм

Здесь важное различие, которое легко перепутать.

**Многопоточный BLAS — ломает.** Внутри одного скалярного произведения потоки складывают частичные суммы в непредсказуемом порядке, `float`-сложение неассоциативно, результат гуляет в младших битах. Критерий приёмки №2 (два прогона с одним сидом → побитово одинаковые `.npz`) с многопоточным BLAS не выполнится.

**Многопроцессный ALS — не ломает.** Шаг обновления пользователей решает каждый `x_u` **независимо** при фиксированной `Y`. Разбиение пользователей по воркерам не меняет ни одного вычисления — меняется только то, кто его выполняет. При фиксированном разбиении (например, по остатку индекса) результат побитово тот же, что и в одном процессе.

Поэтому в `train.py`:

```python
import os
os.environ["VECLIB_MAXIMUM_THREADS"] = "1"   # BLAS строго однопоточный
os.environ["OMP_NUM_THREADS"] = "1"
os.environ["OPENBLAS_NUM_THREADS"] = "1"
import numpy as np
```

и отдельно — флаг `--jobs N` для `multiprocessing.Pool` поверх независимых строк. Разбиение задаётся детерминированно (`range(n_users)` нарезается на N равных срезов), результаты собираются в исходном порядке.

Потеря от однопоточного BLAS здесь близка к нулю: матрицы в решателе `32 × 32`, такие размеры BLAS всё равно не распараллеливает. Весь выигрыш от железа берётся процессами, а не потоками.

Практически: `--jobs 8` даёт 4–6× (не 8× — упирается в память и в gather `Y[idx]`, а не в арифметику). Для модели категорий это не нужно, она и так считается за пару минут; для товарной модели — заметная разница.

Проверить, с чем собран numpy: `python -c "import numpy; numpy.show_config()"` — ожидаем `accelerate` или `openblas`, оба подходят.

### Что не ставим

- **`implicit`** — нужен `brew install libomp`, сборки под ARM исторически ломкие, а её многопоточность пришлось бы отключить ради детерминизма. Свой ALS — это ~40 строк на numpy, плюс он даёт fold-in бесплатно (та же функция, что в обучении).
- **PyTorch / MLX** — избыточно для матриц такого размера, плюс 2+ ГБ зависимостей.
- Зависимости пакета остаются ровно: `numpy`, `scipy`, `pandas`.

### Диск и рабочий цикл

1 ТБ снимает вопрос экономии места, и это стоит использовать в свою пользу — держать три уровня данных одновременно:

| Файл | Размер | Зачем |
|---|---|---|
| сырые CSV RetailHero | ~4,2 ГБ | источник, читается один раз |
| `purchases.parquet` | ~1 ГБ | рабочий кэш, читается за секунды |
| `purchases_sample.parquet` (1 % чеков) | ~10 МБ | цикл разработки: прогон за секунды |
| артефакты моделей | десятки МБ | результат |

**Сэмпл на 1 % — самое полезное здесь.** Пока пишешь и отлаживаешь `matrix.py` и `als.py`, полный датасет не нужен: код проверяется на сэмпле за секунды, полный прогон запускается один раз, когда логика уже верна. Сэмплирование — по хешу `receipt_id`, чтобы чеки не разрывались и выборка была воспроизводимой.

### Реалистичные ожидания по времени

Замеры сделаны на слабом 2-ядерном x86 и пересчитаны под M5. Троттлинга нет, поэтому диапазоны узкие.

| Шаг | 1 процесс | `--jobs 8` |
|---|---|---|
| Первое чтение `purchases.csv` (pyarrow) | 1,5–3 мин | — |
| То же из parquet-кэша | секунды | — |
| Прогон на 1 %-сэмпле (цикл разработки) | < 10 сек | — |
| Модель A (user × category, 400k юзеров) | 2–3 мин | 30–45 сек |
| Модель B на 2 млн чеков | 5–7 мин | 1–2 мин |
| Модель B на полных ~7 млн чеков | 20–25 мин | **4–6 мин** |
| Обе модели на синтетике `sim/` | < 1 сек | — |
| Инференс `recommend_categories` на одном юзере | < 5 мс | — |

Вывод по объёму данных: **сабсемпл чеков больше не обязателен.** Полная товарная модель на 7 млн чеков считается за 4–6 минут — можно учить на всём. Флаг `--max-receipts` остаётся, но его роль меняется: это ускоритель для цикла разработки, а не вынужденная мера.

Два требования к `train.py` при этом сохраняются:

1. **Кэш в parquet** после первого чтения CSV — иначе полторы-три минуты парсинга платятся на каждом прогоне.
2. **Раздельные подкоманды** `--model categories` и `--model companions`, чтобы не пересчитывать одну при правке другой.

### `float32` вместо `float64`

Замер показал двукратное ускорение на `float32` при той же математике. Точности для факторов ALS хватает с запасом, а детерминизм от разрядности не зависит — он про фиксированный сид, однопоточный BLAS и фиксированный порядок обхода. **Матрица взаимодействий и факторы — `float32`**, накопление `YtY` — в `float64`, чтобы не терять точность при суммировании по всем строкам.

### Про остальную команду

Код пишется под эту машину, но не должен требовать её. Два места, где это важно: чанковое чтение (`--chunksize`) остаётся рабочей опцией, и `--jobs` по умолчанию = 1. На ноутбуке без активного охлаждения полный прогон товарной модели войдёт в троттлинг и займёт 30–45 минут вместо 20–25 — там нужен `--max-receipts 2_000_000`.

## 2. Как грузим датасет

**Единый интерфейс — стриминг**, чтобы 45,8 млн строк RetailHero и 10 тыс. синтетических профилей шли одним путём.

```python
# types.py
@dataclass(frozen=True, slots=True)
class Interaction:
    user_id: str
    receipt_id: str
    category: str
    sku: str | None
    ts_week: str      # "2026-W14"
    amount: float

# sources/base.py
class Source(Protocol):
    def stream(self) -> Iterator[Interaction]: ...
```

### RetailHero

Скачивание: `huggingface_hub.snapshot_download("pytorch-lifestream/retailhero-uplift")` либо `sklift.datasets.fetch_x5()`. Файлы кладём в `recsys/data/` и добавляем в `.gitignore` — в репозиторий не коммитим.

Чтение `purchases.csv` — целиком, `pandas.read_csv(usecols=[...], engine="pyarrow")` с немедленным переводом идентификаторов в `int32`-коды (§0, «Память: главная ловушка»). На 32 ГБ это безопасно и быстрее почанковой сборки. Опция `--chunksize N` включает почанковый путь для машин с меньшей памятью. `products.csv` (43 тыс. строк) грузится целиком как справочник `product_id -> category`.

Маппинг:

| CSV | Interaction |
|---|---|
| `client_id` | `user_id` |
| `transaction_id` | `receipt_id` |
| `product_id` → `products.level_3` (или `segment_id`) | `category` |
| `product_id` | `sku` |
| `transaction_datetime` → ISO-неделя | `ts_week` |
| `trn_sum_from_iss` | `amount` |

Сборка матрицы: коды из `.cat.codes` уже являются индексами, поэтому `coo_matrix((values, (user_codes, cat_codes)))` строится одним вызовом, `.tocsr()` сам складывает дубликаты. Словари индексов сохраняются из `.cat.categories`.

В почанковом режиме (`--chunksize`) — тот же результат по частям: каждый чанк превращается в `coo`, приводится к `csr` и суммируется с аккумулятором (`csr += csr`), пик по памяти равен одному чанку. Словари при этом собираются первым проходом по файлу, значения — вторым.

Сабсемпл `--max-receipts N` (детерминированный, по хешу `receipt_id`) — не обязателен: полный объём считается за приемлемое время (§0). Используется как ускоритель цикла разработки и как запасной вариант на слабой машине. Для отладки предусмотреть `--sample-frac 0.01` с сохранением в отдельный parquet.

### Sim

`SimSource(events: list[dict])` — берёт то, что уже отдаёт `gaming_sim.generator`, разворачивает `category_list`/`sku_list` в отдельные `Interaction`. Никакого I/O.

## 3. На чём учится ALS

**Две независимые модели, две разные матрицы.** Это не одна модель с двумя выходами.

### Модель A — категории (персональный вкус)

Матрица `user × category`, implicit feedback.

```
value[u,c] = Σ по чекам пользователя u в категории c:  0.5 ** (age_weeks / 8)
confidence C[u,c] = 1 + alpha * value[u,c]        # alpha = 20
preference p[u,c] = 1 если value > 0 иначе 0
```

Экспоненциальное затухание с полураспадом 8 недель — свежие покупки весят больше. Сумму чека в вес **не** кладём: иначе модель уедет в дорогие категории вместо интересных.

На выходе шиппим только `Y` (`n_categories × k`) — матрицу факторов категорий. Факторы пользователей не сохраняем: новый пользователь получает вектор через fold-in.

### Модель B — сопутствующие товары (свойство товара, не пользователя)

Матрица `receipt × sku`, бинарная. «Пользователь» здесь — чек. Товары, попадающие в похожие чеки, окажутся рядом в пространстве.

На выходе шиппим `Z` (`n_skus × k`) и вектор популярности `pop[sku]` (доля чеков с товаром).

**Почему именно так**: интерес к категории — свойство *человека*, поэтому матрица по пользователям. «Что берут вместе» — свойство *корзины*, поэтому матрица по чекам. Если считать компаньонов по user×sku, получится «что человек покупает вообще», а не «что идёт в комплекте».

### Параметры

```
k        = min(32, n_categories // 2)   для модели A;  32 для модели B
lambda   = 0.1
alpha    = 20
iters    = 12
dtype    = float32   # факторы и матрица; накопление YtY — в float64, см. §0
seed     = 0    # np.random.default_rng(0).normal(0, 0.01, ...)
```

Детерминизм обязателен: BLAS в один поток (§0, ограничение 3), фиксированный порядок обхода, `np.linalg.solve` (не итеративные солверы). Тест: два прогона с одним сидом дают побитово равные факторы.

### Ядро ALS

Один и тот же шаг используется и в обучении, и в инференсе:

```python
def solve_vector(Y, YtY, idx, conf, lam):
    """Hu, Koren, Volinsky 2008. idx — ненулевые позиции, conf — их confidence."""
    Yi = Y[idx]                                  # (nnz, k)
    A = YtY + Yi.T @ ((conf - 1)[:, None] * Yi) + lam * np.eye(Y.shape[1])
    b = Yi.T @ conf                              # p = 1 на ненулевых
    return np.linalg.solve(A, b)
```

`fit` — чередование: посчитать все `x_u` при фиксированной `Y`, потом все `y_c` при фиксированной `X`, 15 раз. `fold_in(Y, YtY, idx, conf, lam)` — это ровно один вызов `solve_vector`. Отдельного кода для инференса не пишем.

### Артефакт

`recsys/artifacts/als_v0.meta.json` + `als_v0.npz`.

```json
{
  "version": "als-v0",
  "source": "retailhero|sim",
  "trained_at": "2026-09-05",
  "k": 32, "lambda": 0.1, "alpha": 20, "iters": 12, "seed": 0, "dtype": "float32",
  "categories": ["dairy", "..."],
  "skus": ["...", "..."],
  "sku_category": {"sku-1": "dairy"}

```

`.npz`: `Y`, `Z`, `pop`. Инференс читает артефакт один раз (`lru_cache`), обучение в рантайме запрещено.

## 4. Как разделены три задачи

Три разных вопроса, три разных механизма. Смешивать их в одну модель нельзя.

| Задача | Вопрос | Механизм | Персонально? |
|---|---|---|---|
| Категории | что этому человеку интересно | ALS модель A + fold-in | да |
| Сопутствующие товары | что идёт в комплекте к этому | ALS модель B, cosine между товарами | нет, контекст товара |
| Скидка / промо | какую акцию показать и насколько сильную | join по категории + правило от уровня | не ML |

**Скидка — не задача ML.** Промо приходят от маркетологов с уже заданной категорией. Рекомендатель отдаёт шортлист категорий; дальше это обычный детерминированный join `promo.category in shortlist`, ранжирование внутри и выбор «мощности» правилом от уровня и бюджета. Никакая модель скидку не генерирует и не предсказывает — иначе экономику будет невозможно защитить.

Поток целиком:

```
история покупок
   → [ALS A] топ-K категорий, минус активные          ← recsys
   → фильтр пула промо по этим категориям             ← engine
   → ранжирование промо                               ← engine (скор из recsys как фича)
   → выбор tier скидки по уровню и бюджету            ← engine (правило, ledger)
   → [ALS B] компаньоны для объяснения «почему это вам» ← recsys
```

## 5. Как работает ранжирование

Не просто dot product. **Две стадии** — это важно.

### Стадия 1 — retrieval, чистый dot product

```python
u = fold_in(Y, YtY, idx_of_user_categories, confidences, lam)   # (k,)
s = Y @ u                                                        # (n_categories,)
s[[idx of c in exclude]] = -inf
top_K = argsort(-s)[:K]                                          # K = 20
```

Здесь dot, а не cosine, сознательно: норма вектора категории коррелирует с её популярностью, а для «что вообще стоит предложить» популярность — полезный сигнал.

### Стадия 2 — ранжирование, линейная смесь

Сырой ALS-скор нельзя отдавать как финальный порядок: он не калиброван между пользователями (разные нормы `u`), и в него не входят бизнес-факторы. Поэтому нормализуем внутри кандидатов одного пользователя и подмешиваем остальное:

```
als_norm  = (s_c - min(s over top_K)) / (max - min + eps)     # min-max внутри кандидатов
score = w_als      * als_norm
      + w_recency  * 1 / (1 + recency_weeks_c)
      + w_margin   * margin_impact_p / max_margin
      + w_novelty  * novelty_p        # промо не показывалось этому пользователю
```

Веса — в конфиге, не в модели. Это сохраняет объяснимость: для любой карточки можно назвать, какой член дал вклад. Такая же структура, как в текущем `promo.py`, только `category_match` из RFM заменён на нормализованный ALS-скор.

Тай-брейк детерминированный: `(-score, -margin_impact, promo_id)`.

### Компаньоны — cosine, не dot

```python
sim(a, b) = (z_a @ z_b) / (|z_a| * |z_b|) - beta * log1p(pop_b)      # beta ~ 0.1
```

Здесь популярность — **шум**, а не сигнал: без штрафа компаньоном ко всему окажутся хлеб и молоко. Cosine убирает эффект нормы, штраф добивает остаточную популярность. Кандидаты — объединение соседей товаров корзины, минус сами эти товары, минус то, что пользователь и так берёт регулярно.

### Cold start

Нет истории → `u` вырождается в ноль → возвращаем топ категорий по популярности из артефакта и помечаем результат `is_fallback=True`. Engine уже умеет обрабатывать такой признак (`cold_start_fallback`).

## 7. CLI обучения

```bash
python -m recsys.train --source sim        --out artifacts/als_v0
python -m recsys.train --source retailhero --data recsys/data --max-receipts 5000000 --out artifacts/als_rh
```

Скрипт: `Source.stream()` → `matrix.build()` → `als.fit()` × 2 модели → `artifacts.save()`. Печатает размеры матриц, sparsity, время, финальный loss на итерациях.

## 8. Критерии приёмки

1. `recsys` не импортирует `gaming_engine` — проверяется тестом на `ast`-обход импортов.
2. Два прогона `train.py` с одним сидом дают побитово идентичные `.npz`.
3. `recall@5` на leave-last-week-out ≥ 0.6 на sim-популяции: спрятать последнюю неделю, проверить, попала ли реально купленная категория в топ-5 при условии, что её не было в `exclude`.
4. Категории из `exclude` никогда не появляются в выдаче.
5. Профиль без истории отдаёт непустой результат с `is_fallback=True`, без исключений.
6. Инференс не обучает модель: тест мокает `als.fit` и падает, если он вызван.
7. Время `recommend_categories` на одном пользователе < 5 мс на артефакте RetailHero.
