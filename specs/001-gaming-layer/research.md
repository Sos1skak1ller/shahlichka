# Phase 0 Research: Персональный игровой слой Х5 Клуб

Дата: 2026-09-03. Вход: `spec.md` (+ Clarifications 2026-09-03), `.specify/memory/constitution.md` v1.0.0,
`docs/TZ_X5_gaming_layer.md` v0.1.

Спецификация не содержит блокирующих `NEEDS CLARIFICATION` — пять уточнений закрыты на
сессии клэрификации. Ниже — технические решения плана, каждое с обоснованием и
отклонёнными альтернативами.

---

## R1. Разделение языков: Python-ядро + React-фронт

**Decision**: Расчётное ядро и симуляция — Python 3.11. Демо-фронт — React 18 + TypeScript,
собранный в статичный бандл. Связь — только через заранее сгенерированные JSON-фикстуры,
валидируемые общей JSON Schema. В рантайме демо фронт не вызывает Python.

**Rationale**:
- ТЗ 8.4 прямо фиксирует React-фронт на статичных фикстурах «чтобы демо не падало от
  сети/нагрузки на сцене» → фронт обязан работать без бэкенда.
- Классический ML (логистическая регрессия, при апгрейде LightGBM, SHAP), синтетическая
  популяция и когортная симуляция — родная территория Python (`scikit-learn`, `numpy`,
  `pandas`); переписывать это на TS — рост сложности без выгоды (нарушает принцип II).
- Статичные фикстуры физически разрывают демо и любой серверный сбой → SC-011.

**Alternatives considered**:
- *Тонкий Python-API под фронт в демо* — отклонено: сеть на сцене = риск отказа, прямо
  назван в ТЗ как то, чего избегаем.
- *Полностью TS (ядро на Node)* — отклонено: теряем ML-экосистему, дублируем расчёт.
- *Только Python + серверный рендер экранов* — отклонено: жюри ждёт кликабельный
  прототип из 3 экранов, React уместнее.

## R2. Детерминизм расчётного ядра

**Decision**: `engine/` — чистые функции над явным состоянием, без обращений к
системным часам и без скрытого глобального состояния. Время берётся только из
`timestamp` события. Любая стохастика (в `sim/`, не в `engine/`) идёт через один
`numpy.random.Generator` с явным сидом, прокинутым в `SimulationRun.parameters`.
Порядок обработки событий — стабильная сортировка по `(timestamp, receipt_id)`.

**Rationale**: SC-005 (уровень аватара воспроизводим на 30–50 историях), SC-006 (demo
== sim), FR-031 (один код — один результат) выполнимы только при полном детерминизме.
Тест паритета `sim/tests/test_parity.py` в CI ловит регрессии.

**Alternatives considered**:
- *Разрешить wall-clock для «недельных» границ* — отклонено: делает прогоны
  невоспроизводимыми; вместо этого «неделя» = ISO-неделя от `timestamp` события.
- *Отдельные реализации для demo и sim с ручной сверкой* — отклонено, нарушает принцип IV
  и FR-031.

## R3. Генерация персонального челленджа (замена LLM-агента — отклонение №1)

**Decision**: Двухступенчатый classic-recsys пайплайн:
1. **Feature builder** — по потоку `PurchaseEvent` строит RFM-профиль по категориям
   (recency / frequency / monetary), архетип, текущий уровень аватара.
2. **Candidate generation** — фильтрует `ChallengeTemplate` по `eligibility_rules`
   (бюджетный потолок, доступные категории пользователя, не показанные за последние K
   недель шаблоны).
3. **Ranking** — `sklearn.linear_model.LogisticRegression` на синтетических метках
   отклика из `sim/`; топ-1 кандидат заполняется параметрами (категория / N / дедлайн /
   награда), текст собирается подстановкой в шаблонную строку (`assemble.py`) — без
   свободной генерации.
4. **Fallback** — если история пуста (холодный старт) или пул шаблонов сегмента исчерпан:
   rule-based челлендж по сегменту с `generated_by = "fallback"`.
5. **Anti-fatigue** — после `config.ANTI_FATIGUE_N` циклов без отклика `timing.py`
   переключает `mechanic_type`.

**Rationale**: закрывает функциональное требование «персональный челлендж по истории
покупок» детерминированно и объяснимо, без guardrail-валидации на каждый вызов
(принцип II, FR-009/010/013/014). Текст для защиты — в spec §Assumptions и ТЗ 1.3.

**Alternatives considered**:
- *LLM-агент (буква кейса)* — отклонено осознанно (отклонение №1): непредсказуемость
  вывода, стоимость токенов, хуже объясняется жюри, риск галлюцинаций на демо.
- *LightGBM-ранкер сразу* — отложено как апгрейд: для MVP-меток из синтетики логрег
  достаточно и полностью интерпретируем; LightGBM + SHAP включаем, если останется время.
- *Contextual bandit (LinUCB / Thompson) для тайминга* — отложено: MVP — rule-based
  (ТЗ 10.2).

## R4. Антифрод: взвешенный scorecard

**Decision**: Интерпретируемый взвешенный scorecard с фиксированным явным порогом.
Фичи: скорость чеков (чек/час на профиль), отклонение суммы/частоты от паттерна
архетипа, совпадение `device_id_hash` / `payment_instrument_hash` между «разными»
рефералами, всплеск исходящих инвайтов. `score = Σ wᵢ·fᵢ`; вклад каждой фичи
(`wᵢ·fᵢ`) кладётся в `explanation{}`. Две границы → три полосы: `pass` / `review` /
`block`. На границе — решение в сторону **строже** (ровно порог блокировки ⇒ block).
Метрика приёмки — **precision на фрод-классе** на помеченном наборе синтетических
паттернов, цель ≥ 0.90 (иллюстративный ориентир, см. R8); recall может быть ниже.

**Обработка полосы `review`** (клэрификация Q5): награда **удерживается** — не
начисляется и не списывается из `budget_cap`. `engine` планирует авто-разрешение через
`config.REVIEW_HOLD` модельного времени по детерминированному правилу: `pass`, если за
время удержания по сущности не накопилось новых сигналов риска; иначе `block`. Исход и
время пишутся в `FraudScore.review_outcome` / `review_resolved_at`.

**Rationale**: принцип II (порог объясним), FR-015/015a/016/017/020, кейс «precision >
recall». Апгрейд — градиентный бустинг поверх с SHAP, но решающий порог остаётся
фиксированным и объяснимым.

**Alternatives considered**:
- *Только ML-классификатор без явного порога* — отклонено: непрозрачно для жюри.
- *Ручная модерация полосы review* — отклонено: в MVP нет команды антифрода (Q5);
  детерминированное авто-разрешение сохраняет воспроизводимость demo/sim.
- *accuracy как метрика* — отклонено: при дисбалансе классов вводит в заблуждение
  (ТЗ 10.4).

## R5. Экономика награды и бюджетный потолок

**Decision**: `RewardLedger` — запись на `(user_id, iso_week)`: `budget_cap`,
`accrued_reward`, `spent_to_date`. `budget_cap = config.BUDGET_CAP_PCT ×
historical_weekly_margin(user)`, где `historical_weekly_margin` берётся из
иллюстративной таблицы маржи по архетипу (R8). Перед любой выдачей — pre-check:
1. `reward_cost + spent_to_date ≤ budget_cap` (недельный потолок), И
2. `reward_cost ≤ expected_margin_uplift(mechanic, user)` (инвариант кейса).
Нарушение (1) или (2) ⇒ награда не начисляется, событие логируется
(`budget_exceeded` / `economy_invariant_violation`). Реферальная награда добавляется в
`accrued_reward` только при переходе `referral → reward_released` (отложенность,
FR-021), списывается из потолка **пригласившего**.

**Rationale**: принцип III, FR-018/019/023; критерий успеха кейса «стоимость награды ≤
ожидаемый прирост маржи»; недельный потолок (а не только лимит на операцию) не даёт
бюджету «протекать» мелкими начислениями (ТЗ 12).

**Alternatives considered**:
- *Постфактум-аудит стоимости наград* — отклонено, прямо противоречит принципу III.
- *Лимит только на одну операцию* — отклонено (ТЗ 12: бюджет протекает).

## R6. Когортная симуляция

**Decision**: `sim/population.py` сэмплирует популяцию (1–10 тыс.) пропорционально долям
сегментов по трём сетям из `fixtures/data/segment_mix.json` (§3.1 ТЗ) с повышенным
весом на «пользователей МП». `sim/runner.py` прогоняет **две когорты из одного и того
же сэмпла**: `treatment` (флаг `gaming_layer_enabled = True` в `engine`) и `control`
(`False`). `sim/metrics.py` считает по каждой когорте primary (возврат D7 без push,
частота покупок, средний чек) и guardrail (retention, новые по рефералке, позиций в
корзине, длина сессии). Заявляемый сдвиг = `metric(treatment) − metric(control)`.
`report.py` пишет отчёт по `simulation-report.schema.json`, включая
`roi = Δmargin(treatment − control) − Σ reward_cost`.

**Rationale**: клэрификация Q2, FR-032/032a/033, SC-003/007/010. Сдвиг в п.п. измерим
только относительно baseline → нужна control-когорта.

**Alternatives considered**:
- *Только treatment + внешние baseline-числа* — отклонено: числа неоткуда взять честно
  на синтетике.
- *Paired within-subject (те же юзеры со слоем выкл)* — рассмотрено, оставлено как
  возможный доп-режим отчёта; основной — независимые когорты из одного микса (проще
  объясняется).
- *Полноценная agent-based модель* — отклонено (ТЗ 10.5): когортное сэмплирование
  вероятности отклика по архетипу — осознанный компромисс ради скорости прогона.

## R7. Контракт данных: JSON Schema как единый источник истины

**Decision**: `contracts/*.schema.json` (Draft 2020-12) — канонические определения:
`purchase-event` (вход движка), три экранных контракта (`profile-screen`,
`challenge-screen`, `referral-screen`) и `simulation-report`. `scripts/gen-contract-types.sh`
генерирует TS-типы для `web/src/contract/` и pydantic-модели для
`engine/src/gaming_engine/contracts.py`. Фронт валидирует загруженную фикстуру `zod`-схемой,
собранной из того же JSON Schema; движок валидирует вход/выход pydantic. Контрактный
тест гоняет все фикстуры `fixtures/out/*.json` против схем.

**Rationale**: FR-030, spec §Assumptions («фикстура — заменяемая реализация того же
интерфейса»). Единый источник не даёт форме данных разойтись между Python и TS при
переходе к реальному бэкенду.

**Alternatives considered**:
- *Отдельные типы на фронте и в движке вручную* — отклонено: расходятся со временем.
- *OpenAPI* — избыточно: в демо нет HTTP-эндпоинтов; нужен контракт формы данных, не
  транспорта.

## R8. Иллюстративные константы (`engine/config.py`)

Спецификация фиксирует **правила**, а не числа; ТЗ помечает конкретные значения как
открытые (сегмент, маржа, N, пороги, число стадий). План принимает рабочие
иллюстративные значения, **явно помеченные как иллюстративные** для защиты. Все — в
одном модуле `config.py`, чтобы команда меняла их в одном месте.

| Константа | Иллюстративное значение | Источник / примечание |
|---|---|---|
| `AVATAR_LEVELS` | 5 уровней, пороги накопленной экономии: 0 / 500 / 1500 / 3500 / 7000 ₽ | ТЗ: «4–5 визуальных стадий»; кривая с ростом шага |
| `VISUAL_STAGES` | 5 (1:1 с уровнями) | ТЗ 9 |
| `ANTI_FATIGUE_N` | 3 цикла без отклика | открытый вопрос ТЗ 13 №4 |
| `BUDGET_CAP_PCT` | 20% от исторической недельной маржи | открытый вопрос ТЗ 12 |
| `WEEKLY_MARGIN_BY_ARCHETYPE` | эконом-охотник 60 ₽ / лоялист 120 ₽ / спящий 30 ₽ / кросс-шоппер 150 ₽ | иллюстративно (кейс не даёт) |
| `REVIEW_HOLD` | 72 ч модельного времени | клэрификация Q5 |
| `REFERRAL_WINDOW` | 30 дней на первую покупку приглашённого | spec §Assumptions |
| `FRAUD_THRESHOLDS` | review ≥ 0.5, block ≥ 0.8 (по нормированному score) | подбирается под precision ≥ 0.90 на размеченном наборе |
| `PRECISION_TARGET` | 0.90 на фрод-классе | spec §Assumptions, ТЗ 13 №6 |
| `SEGMENT` | «родители с детьми до 3 лет», пользователи МП | spec §Assumptions, ТЗ 3.2 (ратификация за командой) |

**Rationale**: даёт движку запускаться и симуляции — считать, не пряча за это
продуктовые решения; всё правится централизованно после ратификации командой.

## R9. Продуктовое имя без «ИИ»/«AI»

**Decision**: репозиторий и код используют нейтральные технические имена
(`gaming_engine`, `gaming_sim`). Продуктовое имя для экранов демо — плейсхолдер
«Х5 Клуб · Рост» (без «AI»/«ИИ»), финал за командой (открытый вопрос ТЗ 13 №7).

**Rationale**: FR-035; ограничение зафиксировано на доске.
