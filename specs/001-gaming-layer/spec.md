# Feature Specification: Персональный игровой слой Х5 Клуб

**Feature Branch**: `001-gaming-layer`

**Created**: 2026-09-03

**Status**: Draft

**Input**: User description: "Full gaming layer from the TZ" — весь документ `docs/TZ_X5_gaming_layer.md` как одна спецификация фичи (аватар + челленджи + антифрод + симуляция + реферал + ранжирование акций).

## Clarifications

### Session 2026-09-03

- Q: Считает ли систему сумму экономии по чеку сама, или берёт её как есть из входящего события? → A: Синтетический генератор эмитит `saved_amount` в каждом событии покупки; игровой слой принимает его как заданный вход и никогда не пересчитывает.
- Q: Как симуляция получает сдвиги в п.п. для гипотез пилота? → A: Каждый прогон запускает две когорты из одного микса популяции — treatment (игровой слой включён) и control (выключен); каждая метрика считается по когортам, сдвиг = treatment − control.
- Q: Уникально ли идентифицируется событие покупки и идемпотентна ли его обработка? → A: Событие несёт уникальный идентификатор чека; обработка идемпотентна — повторный идентификатор учитывается один раз и игнорируется при последующих доставках; корректировки/возвраты приходят отдельными событиями со ссылкой на этот идентификатор.
- Q: Что сбрасывает стрик покупок пользователя? → A: Стрик считает подряд идущие календарные недели, в каждой из которых есть ≥1 подтверждённая покупка; неделя без подтверждённых покупок сбрасывает стрик в 0.
- Q: Как в MVP разрешается решение «на ревью» без реальной команды антифрода? → A: «На ревью» удерживает награду (не начислена, не списана из бюджета); демо/симуляция авто-разрешает статус через фиксированную задержку по детерминированному правилу (пропустить, если новых сигналов риска не накопилось), исход логируется.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Аватар растёт от реальной экономии (Priority: P1)

Пользователь мобильного приложения (сегмент «родители с детьми до 3 лет») заходит в
раздел «Клуб» и видит на главном экране своего аватара и прогресс-бар. Прогресс
двигает не активность в приложении, а сумма, которую пользователь сэкономил на
покупках (по акциям, «любимым категориям», кешбэку). При достижении порога аватар
переходит на следующий уровень и открывается новая визуальная кастомизация
(скин/аксессуар). Пользователь понимает: чем больше он экономит, регулярно покупая в
одной экосистеме, тем заметнее накопительный результат.

**Why this priority**: Приоритет №1 по RICE (H1) и самая простая в реализации механика
— детерминированная state-machine без ML. Это ядро демо и главный экран: без неё
остальные механики не имеют опоры. Реализованная в одиночку, она уже даёт жизнеспособный
MVP — пользователь видит накопительный смысл своих покупок.

**Independent Test**: Прогнать 30–50 синтетических историй покупок через расчёт
экономии и state-machine аватара; проверить, что уровень и визуальная стадия аватара
воспроизводимо соответствуют накопленной сумме экономии и не зависят от числа заходов
в приложение.

**Acceptance Scenarios**:

1. **Given** пользователь с накопленной экономией ниже первого порога, **When** приходит
   новый подтверждённый чек с суммой экономии, поднимающей накопление выше порога,
   **Then** аватар переходит на следующий уровень и разблокируется новая кастомизация.
2. **Given** пользователь открыл приложение 10 раз без единой покупки, **When** он
   смотрит на главный экран, **Then** уровень аватара и прогресс-бар не изменились.
3. **Given** чек с нулевой или отрицательной экономией, **When** он попадает в систему,
   **Then** прогресс аватара не двигается вперёд.
4. **Given** ранее учтённый чек отменён/возвращён, **When** приходит корректировка,
   **Then** накопленная экономия уменьшается на сумму корректировки, а уровень аватара
   пересчитывается (возможно понижение) с записью в историю переходов.
5. **Given** пользователь достиг максимального уровня, **When** приходят новые чеки с
   экономией, **Then** накопление продолжает расти, новые уровни не создаются, аватар
   остаётся на максимальной визуальной стадии.

### User Story 2 - Персональный недельный челлендж по истории покупок (Priority: P2)

Пользователю раз в неделю предлагается один персональный челлендж вида «купи N раз
категорию X до даты Y — получишь награду Z». Челлендж подбирается по истории покупок
конкретного пользователя (какие категории он берёт, как часто, на какую сумму) и по
текущему уровню аватара, а не выдаётся всем одинаковый. Текст челленджа собирается из
шаблона с подстановкой параметров — без свободной генерации. Выполнение челленджа
подтверждается чеком, а не действием в приложении.

**Why this priority**: Закрывает обязательное требование кейса «персональные челленджи»
(в командной трактовке — ML-пайплайн вместо LLM). Даёт персонализацию и повод вернуться,
но опирается на US1 (уровень аватара — вход для подбора) и на антифрод/экономику (US3).

**Independent Test**: На 30–50 held-out профилях эксперт размечает релевантность
предложенного челленджа; доля релевантных ≥ 70%. Отдельно проверяется, что при
одинаковом сегменте, но разной истории покупок два пользователя получают разные
челленджи, и что каждый выданный челлендж уложен в недельный бюджетный потолок.

**Acceptance Scenarios**:

1. **Given** пользователь с историей регулярных покупок в категории «детское питание»,
   **When** генерируется недельный челлендж, **Then** предложенный челлендж относится к
   категории из его реальной истории и его стоимость награды не превышает бюджетный
   потолок пользователя за неделю.
2. **Given** активный челлендж у пользователя, **When** наступает начало новой недели,
   **Then** новый челлендж не выдаётся, пока текущий не завершён или не истёк.
3. **Given** пользователь без релевантной истории покупок (холодный старт), **When**
   генерируется челлендж, **Then** используется fallback-челлендж по сегменту, помеченный
   соответствующим источником.
4. **Given** пул подходящих шаблонов для сегмента исчерпан на эту неделю, **When**
   запрашивается челлендж, **Then** система выдаёт fallback и фиксирует событие
   «пул исчерпан» для аналитики.
5. **Given** пользователь N циклов подряд не реагировал на челленджи, **When**
   подбирается следующий, **Then** тип механики переключается (anti-fatigue).

### User Story 3 - Антифрод чеков и рефералов + бюджетный потолок награды (Priority: P2)

Система проверяет каждый чек и каждый реферал на накрутку до того, как награда
начислена. Для каждой сущности считается оценка риска с фиксированным явным порогом и
объяснением по каждому признаку; решение — «пропустить», «на ревью» или
«заблокировать». Параллельно ведётся учёт выданных наград против бюджетного потолка,
заданного как процент от исторической маржи пользователя за неделю. Награда не
начисляется, если её стоимость выводит пользователя за потолок или если экономика
награды нарушает инвариант «стоимость награды ≤ ожидаемый прирост маржи».

**Why this priority**: Обязательное требование кейса независимо от набора механик;
«неприемлемо», если награда съедает эффект. Без этого слоя US1/US2/US5 нельзя показывать
жюри. Precision на фрод-классе важнее recall.

**Independent Test**: Прогнать помеченный набор синтетических паттернов (нормальные +
известные фродовые: аномальная скорость чеков, совпадение устройства/платёжного
инструмента у «разных» рефералов, self-referral) и измерить precision именно на
фрод-классе; проверить, что при достижении бюджетного потолка начисления
останавливаются.

**Acceptance Scenarios**:

1. **Given** серия чеков с аномально высокой частотой от одного профиля, **When** они
   проходят скоринг, **Then** оценка риска превышает порог и решение — «заблокировать»
   с объяснением по признаку скорости.
2. **Given** реферал, у которого хэш устройства или платёжного инструмента совпадает с
   пригласившим, **When** приглашённый пытается перейти в статус «зарегистрирован»,
   **Then** переход блокируется как self-referral.
3. **Given** пользователь, чья накопленная за неделю награда достигла бюджетного
   потолка, **When** приходит новое событие, дающее награду, **Then** награда не
   начисляется, событие фиксируется как «превышение бюджета».
4. **Given** оценка риска попала в средний диапазон, **When** принимается решение,
   **Then** сущность помечается «на ревью», награда удерживается (не начислена, не
   списана из бюджета), а по истечении фиксированной задержки статус авто-разрешается по
   детерминированному правилу с записью исхода в журнал.
5. **Given** челлендж с формулой награды, дающей стоимость больше ожидаемого прироста
   маржи, **When** он проходит проверку экономики, **Then** челлендж отклоняется до
   показа пользователю.

### User Story 4 - Когортная симуляция и одностраничный план пилота (Priority: P2)

Аналитик команды запускает офлайн-прогон 1–10 тыс. синтетических профилей через тот же
расчётный стек, что и живое демо. Состав популяции сэмплируется пропорционально
реальным долям сегментов по трём сетям (ТС5/ТСХ/ТСЧ) с весом на пользователей
мобильного приложения. На выходе — набор метрик, разделённых на основные (primary) и
защитные (guardrail), и одностраничный план пилота с гипотезой и формулой ROI.

**Why this priority**: Обязательный по кейсу артефакт (симуляция + план пилота на один
слайд). Нужен для защиты и для проверки инварианта экономики на объёме, но не для
пользовательского пути в демо.

**Independent Test**: Запустить прогон на 1 000 и на 10 000 профилей; убедиться, что
доли архетипов/сегментов в популяции соответствуют заданному миксу по трём сетям, что
считаются все primary и guardrail метрики, и что результаты не расходятся с расчётом
того же сценария в демо-контуре.

**Acceptance Scenarios**:

1. **Given** заданный размер популяции в диапазоне 1–10 тыс. и микс сегментов по трём
   сетям, **When** запускается прогон, **Then** сгенерированная популяция воспроизводит
   заданные доли сегментов и архетипов в пределах допустимого отклонения.
2. **Given** завершённый прогон, **When** формируется отчёт, **Then** он содержит
   основные метрики (возврат D7 без push, частота покупок, средний чек) и защитные
   метрики (retention, новые пользователи по рефералке, число позиций в корзине, длина
   сессии) — по обеим когортам (treatment и control), со сдвигом treatment − control.
3. **Given** один и тот же сценарий, **When** он прогоняется в симуляции и
   воспроизводится в демо-контуре, **Then** ключевые числа (уровень аватара, стоимость
   награды) совпадают.
4. **Given** отчёт по прогону, **When** считается формула ROI пилота, **Then** она равна
   «прирост маржи − стоимость всех выданных наград» и согласуется с допущениями по
   марже.

### User Story 5 - Реферальная программа с отложенной наградой (Priority: P3)

Пользователь приглашает знакомого по персональной ссылке. Приглашённый проходит путь:
приглашён → зарегистрирован → совершил подтверждённую чеком покупку → награда выдана.
Награда пригласившему и приглашённому начисляется только после подтверждённой покупки,
а не сразу после регистрации, и проходит через антифрод (US3).

**Why this priority**: Закрывает требование кейса про реферальный канал и «упущенный
органический рост», но не критично для ядра демо; зависит от антифрода и экономики.

**Independent Test**: Провести синтетического приглашённого по всем статусам и убедиться,
что награда не выдаётся до статуса «совершил покупку»; провести приглашённого с
совпадающим устройством и убедиться, что реферал блокируется.

**Acceptance Scenarios**:

1. **Given** приглашённый зарегистрировался, но ещё не покупал, **When** проверяется
   состояние реферала, **Then** награда не начислена ни одной стороне.
2. **Given** приглашённый совершил первую подтверждённую покупку, **When** реферал
   переходит в финальный статус, **Then** награда выдаётся обеим сторонам и списывается
   из бюджетного потолка пригласившего.
3. **Given** приглашённый так и не совершил покупку в течение допустимого окна, **When**
   окно истекает, **Then** реферал закрывается без награды.
4. **Given** массовые приглашения с признаками накрутки от одного профиля, **When** они
   проходят скоринг, **Then** подозрительные рефералы помечаются «на ревью» или
   блокируются.

### User Story 6 - Персонализированное ранжирование акций (Priority: P3)

Пул акций «от маркетинга» ранжируется под профиль пользователя (совпадение категории с
историей покупок, свежесть покупок в категории, маржинальность акции), чтобы наверху
показывались наиболее релевантные предложения, а не случайные.

**Why this priority**: Усиливает персонализацию и связь с маржой, но полностью
опционален для ядра демо и оценивается той же метрикой релевантности, что и челленджи.

**Independent Test**: На 30–50 held-out профилях с ручной разметкой релевантности
проверить hit rate топ-предложений ≥ 70%.

**Acceptance Scenarios**:

1. **Given** пользователь с недавними покупками в категории «гигиена», **When**
   ранжируется пул акций, **Then** акции этой категории оказываются выше акций из
   категорий, которых нет в его истории.
2. **Given** две акции с равной релевантностью по истории, **When** они ранжируются,
   **Then** выше оказывается акция с большей маржинальностью.
3. **Given** пользователь без истории покупок, **When** ранжируется пул, **Then**
   применяется нейтральный порядок по сегменту без ошибки.

---

### Edge Cases

- Чек приходит с суммой экономии, но без списка категорий/SKU — как учитывается в
  прогрессе аватара и доступен ли он для челленджей.
- Одно и то же событие покупки доставлено дважды (одинаковый идентификатор чека) —
  прогресс не должен сдвинуться повторно.
- Корректировка/возврат чека приходит после того, как пользователь уже разблокировал
  кастомизацию за счёт этого чека.
- Бюджетный потолок исчерпан в середине недели — поведение всех механик, выдающих
  награду (челлендж, реферал).
- Пул шаблонов челленджа для сегмента исчерпан на неделю.
- Пользователь холодного старта (нет истории) для челленджа и для ранжирования акций.
- Размер популяции симуляции не позволяет воспроизвести заданный микс сегментов без
  искусственного завышения кластеров.
- Оценка риска ровно на пороге — в какую сторону округляется решение.
- Во время удержания «на ревью» по той же сущности накапливается новый сигнал риска —
  авто-разрешение должно завершиться блокировкой, а не пропуском.
- Приглашённый регистрируется, но никогда не покупает; окно ожидания реферала.
- Один и тот же синтетический сценарий даёт разные числа в демо и в симуляции
  (нарушение инварианта «один код — один результат»).

## Requirements *(mandatory)*

### Functional Requirements

#### Профиль и аватар

- **FR-001**: Система MUST вести профиль игрока, привязанный к обезличенному
  идентификатору карты Х5 Клуб, с полями сегмента, архетипа (синтетика), накопленной
  суммы экономии, текущего уровня аватара и счётчика стрика.
- **FR-002**: Система MUST принимать сумму экономии пользователя (`saved_amount`, а не
  сумму траты) как заданное поле входящего события покупки и добавлять её к накопленной
  экономии профиля; система MUST NOT пересчитывать эту сумму по SKU/акциям.
- **FR-003**: Уровень и визуальная стадия аватара MUST определяться исключительно
  накопленной суммой экономии; активность в приложении и число заходов MUST NOT влиять
  на прогресс.
- **FR-004**: При достижении порога накопленной экономии система MUST повышать уровень
  аватара, разблокировать соответствующую кастомизацию и записывать переход в историю.
- **FR-005**: При отмене/возврате ранее учтённого чека система MUST уменьшать
  накопленную экономию на сумму корректировки и пересчитывать уровень аватара, допуская
  понижение уровня.
- **FR-006**: Стрик MUST считать подряд идущие календарные недели, в каждой из которых
  есть хотя бы одна подтверждённая чеком покупка (открытия приложения не учитываются);
  первая календарная неделя без подтверждённой покупки MUST сбрасывать стрик в 0.
- **FR-007**: Прототип MUST состоять из трёх экранов: профиль/аватар, челлендж, реферал.
  Экран рейтинга экономии MUST NOT реализовываться.

#### Персональный челлендж

- **FR-008**: Система MUST предлагать пользователю не более одного активного
  персонального челленджа одновременно, с недельным циклом обновления.
- **FR-009**: Челлендж MUST подбираться на основе истории покупок конкретного
  пользователя (категории, частота, сумма) и текущего уровня аватара.
- **FR-010**: Текст челленджа MUST собираться из шаблонной строки с подстановкой
  параметров (категория, N, дедлайн, награда); свободная генерация текста MUST NOT
  использоваться.
- **FR-011**: Каждый выданный челлендж MUST нести рассчитанную стоимость награды
  (`budget_cost`) и источник генерации (ранжирование / правило / fallback).
- **FR-012**: Выполнение челленджа MUST подтверждаться чеком, а не действием в
  приложении.
- **FR-013**: При отсутствии релевантной истории (холодный старт) или исчерпании пула
  шаблонов для сегмента система MUST выдавать fallback-челлендж по сегменту с явной
  пометкой источника.
- **FR-014**: После N последовательных циклов без реакции пользователя система MUST
  переключать тип механики челленджа (anti-fatigue); значение N — настраиваемый
  параметр.

#### Антифрод и экономика награды

- **FR-015**: Система MUST синхронно оценивать риск по каждому чеку и каждому рефералу
  до начисления награды, с решением «пропустить» / «на ревью» / «заблокировать».
- **FR-015a**: Решение «на ревью» MUST удерживать связанную награду — она не начисляется
  и не списывается из бюджетного потолка до разрешения статуса. В демо и симуляции
  статус MUST авто-разрешаться через фиксированную задержку по детерминированному правилу
  (по умолчанию: «пропустить», если за время удержания не накопилось новых сигналов
  риска), исход MUST фиксироваться в журнале.
- **FR-016**: Оценка риска MUST использовать фиксированный явный порог и MUST
  сопровождаться объяснением вклада каждого признака.
- **FR-017**: Система MUST блокировать self-referral: при переходе приглашённого в
  статус «зарегистрирован» хэш устройства и хэш платёжного инструмента приглашённого
  MUST отличаться от пригласившего.
- **FR-018**: Система MUST вести учёт выданных наград по пользователю за период против
  бюджетного потолка, заданного как процент от исторической маржи пользователя за
  неделю.
- **FR-019**: Система MUST NOT начислять награду, если её стоимость выводит пользователя
  за недельный бюджетный потолок либо нарушает инвариант «стоимость награды ≤ ожидаемый
  прирост маржи».
- **FR-020**: Качество антифрода MUST измеряться precision на фрод-классе (не accuracy).
- **FR-021**: Реферальная награда MUST быть отложенной и выдаваться только после статуса
  «совершил подтверждённую покупку».

#### Реферальная программа

- **FR-022**: Система MUST вести реферал по состояниям: приглашён → зарегистрирован →
  совершил покупку → награда выдана, с фиксацией времени каждого перехода, а также
  статусом «заблокирован».
- **FR-023**: При переходе в финальный статус система MUST начислять награду обеим
  сторонам и списывать её из бюджетного потолка пригласившего.
- **FR-024**: Если приглашённый не совершил покупку в течение допустимого окна, система
  MUST закрывать реферал без награды.

#### Ранжирование акций

- **FR-025**: Система MUST ранжировать пул акций «от маркетинга» под профиль
  пользователя по совпадению категории с историей, свежести покупок и маржинальности
  акции.
- **FR-026**: При равной релевантности по истории система MUST ставить выше акцию с
  большей маржинальностью.
- **FR-027**: Для пользователя без истории покупок система MUST применять нейтральный
  порядок по сегменту без ошибки.

#### Данные, симуляция, приватность

- **FR-028**: Единственным источником данных MUST быть синтетический генератор чеков,
  профилей и социального графа; реальные данные, витрины и интеграции X5 MUST NOT
  использоваться.
- **FR-029**: Система MUST NOT хранить персональные данные (ФИО, адрес) нигде в игровом
  слое.
- **FR-030**: Событийный поток покупок MUST содержать: уникальный идентификатор чека,
  обезличенный идентификатор пользователя, код магазина, код района, метку времени,
  список SKU, список категорий, сумму чека, сумму экономии, хэш устройства, хэш
  платёжного инструмента; для события-корректировки — ссылку на идентификатор исходного
  чека.
- **FR-030a**: Обработка события покупки MUST быть идемпотентной: повторно доставленное
  событие с уже виденным идентификатором чека MUST учитываться ровно один раз и не
  двигать прогресс аватара, стрик или триггеры челленджа повторно.
- **FR-031**: Один и тот же расчётный код MUST обслуживать и живое демо, и симуляцию;
  результаты одного сценария MUST совпадать в обоих контурах.
- **FR-032**: Симуляция MUST прогонять 1–10 тыс. синтетических профилей, состав
  популяции MUST сэмплироваться пропорционально реальным долям сегментов по трём сетям
  (ТС5/ТСХ/ТСЧ) с весом на пользователей мобильного приложения.
- **FR-032a**: Каждый прогон симуляции MUST формировать две когорты из одного и того же
  микса популяции — treatment (игровой слой включён) и control (игровой слой выключен);
  каждая метрика пилота MUST считаться отдельно по когортам, а заявляемый сдвиг в п.п.
  MUST вычисляться как treatment − control.
- **FR-033**: Отчёт симуляции MUST разделять метрики на основные (primary) и защитные
  (guardrail), приводить их по обеим когортам и MUST включать формулу ROI пилота
  «прирост маржи (treatment − control) − стоимость всех выданных наград».
- **FR-034**: Кешбэк-баллы Х5 Клуб и награды игрового слоя MUST оставаться разными,
  непересекающимися валютами.
- **FR-035**: Название продукта MUST NOT содержать слово «ИИ» / «AI».
- **FR-036**: Любое осознанное отклонение от буквального текста кейса MUST быть помечено
  и иметь обоснование и текст для защиты (на момент старта зафиксированы два: замена
  LLM-агента на ML-пайплайн; исключение рейтинга экономии).

### Key Entities *(include if feature involves data)*

- **Профиль игрока (User)**: обезличенный игрок; сегмент, архетип, дата регистрации,
  хэш устройства, хэш платёжного инструмента, накопленная экономия, уровень аватара,
  стрик.
- **Аватар (Avatar)**: 1:1 с профилем; уровень, визуальная стадия (1 из 4–5), состояние,
  время последнего перехода, история переходов.
- **Событие покупки (PurchaseEvent)**: атомарный факт покупки с суммой экономии;
  уникальный идентификатор чека (ключ идемпотентности), опциональная ссылка на исходный
  чек для корректировок; входной сигнал для аватара, триггера челленджа и антифрода.
- **Шаблон челленджа (ChallengeTemplate)**: тип механики, шаблон условия, формула
  награды, правила применимости.
- **Челлендж (Challenge)**: конкретный экземпляр под пользователя/сегмент; ключ кэша
  (сегмент + неделя), параметры, источник генерации, стоимость награды, статус, окно
  действия.
- **Реферал (Referral)**: связь пригласивший ↔ приглашённый; статус, метки времени
  переходов, сумма награды, ссылка на оценку риска.
- **Акция (Promo)** и **Ранжирование акций (PromoRanking)**: пул предложений от
  маркетинга и его персональный порядок для пользователя с признаком «показано/погашено».
- **Оценка риска (FraudScore)**: тип сущности (чек/реферал), значение, использованный
  порог, решение (пропустить/на ревью/заблокировать), для «на ревью» — исход и время
  авто-разрешения, вектор признаков, объяснение.
- **Реестр наград (RewardLedger)**: по пользователю и периоду — начисленная награда,
  бюджетный потолок (% недельной маржи), израсходовано на дату.
- **Синтетический профиль (SyntheticUserProfile)**: архетип, код сети, сегмент,
  параметры генерации, распределение поведения.
- **Прогон симуляции (SimulationRun)**: размер популяции (1–10 тыс.), микс по сетям и
  сегментам, параметры.
- **Метрика пилота (PilotMetric)**: имя, вид (primary/guardrail), когорта
  (treatment/control), значение, период.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: На 30–50 held-out профилях доля релевантных персональных челленджей
  (экспертная разметка) ≥ 70%.
- **SC-002**: На 30–50 held-out профилях hit rate топ-предложений персонального
  ранжирования акций ≥ 70%.
- **SC-003**: Инвариант экономики «суммарная стоимость выданных наград ≤ ожидаемый
  прирост маржи» выполняется на каждом прогоне симуляции 1–10 тыс. профилей.
- **SC-004**: Precision антифрода на фрод-классе ≥ 0,90 на помеченном наборе
  синтетических паттернов; recall может быть ниже.
- **SC-005**: На 30–50 воспроизведённых историях покупок уровень аватара совпадает с
  ожидаемым в 100% случаев (детерминированность state-machine).
- **SC-006**: Один и тот же сценарий даёт совпадающие ключевые числа (уровень аватара,
  стоимость награды) в демо-контуре и в симуляции.
- **SC-007**: Симуляция успешно отрабатывает популяции 1 000 и 10 000 профилей и
  формирует полный набор primary и guardrail метрик и формулу ROI пилота.
- **SC-008**: Игровой слой не хранит ни одного поля персональных данных (ФИО/адрес) —
  проверяется ревизией доменной модели.
- **SC-009**: Прототип содержит ровно 3 рабочих экрана; в названии продукта отсутствует
  слово «ИИ»/«AI».
- **SC-010**: Гипотезы пилота сформулированы с целевыми сдвигами: возврат D7 без push
  +4 п.п. (H1), покупки в ≥3 из 4 недель месяца +5 п.п. (H2), продолжение челленджа 3+
  недели подряд при равном бюджете +6 п.п. (H3) — и проверяемы в симуляции.
- **SC-011**: На демо ни один пользовательский путь (3 экрана) не зависит от сети, базы
  данных или внешней нагрузки.

## Assumptions

- **Целевой сегмент** — «взрослые с детьми до 3 лет, пользователи мобильного
  приложения» во всех трёх сетях; вывод сделан из присланного распределения сегментов,
  финальная ратификация — за командой (открытый вопрос ТЗ 13 №1).
- **Цифры маржи и среднего чека** для расчёта бюджетного потолка и ROI берутся как
  иллюстративное допущение и явно помечаются как иллюстративные на защите (кейс их не
  даёт — открытый вопрос ТЗ 12).
- **Целевая precision антифрода ≥ 0,90** принята как рабочий ориентир; конкретный набор
  признаков и порог scorecard — открытый вопрос ТЗ 13 №6.
- **Значение N** для anti-fatigue переключения челленджа — настраиваемый параметр,
  конкретное значение фиксируется командой (открытый вопрос ТЗ 13 №4).
- **Разметку релевантности** челленджей/акций для hit rate выполняет назначенный член
  команды по чек-листу (открытый вопрос ТЗ 13 №3).
- **Пороги уровней аватара, формулы наград и число визуальных стадий (4–5)** —
  подбираются командой при реализации; спецификация фиксирует правила, а не числа.
- **Окно ожидания реферала** (срок, за который приглашённый должен совершить покупку) —
  фиксируется командой; по умолчанию соответствует одному месячному циклу.
- **Демо-контур** работает на статичных фикстурах вместо БД/очередей; контракты
  интерфейсов спроектированы так, что фикстура — заменяемая реализация того же
  интерфейса (детали — на этапе плана).
- **Вне скоупа** (жёстко по кейсу): боевые CRM/кассы/push, промышленная нагрузка,
  реальные списания, ПДн и внутренние витрины X5, полный антифрод-контур, модерация
  контента, магазин скинов, отдельное приложение, полный юридический/секьюрити-анализ.
- **Рейтинг экономии (дом/район/город)** исключён из скоупа целиком (осознанное
  отклонение №2).
- **Персональный челлендж** реализуется объяснимым расчётным пайплайном (шаблоны +
  ранжирование) вместо LLM-агента (осознанное отклонение №1).

## Dependencies

- Синтетический генератор чеков, профилей и социального графа — единственный источник
  данных для всех пользовательских историй.
- Реальное распределение долей сегментов по трём сетям (ТС5/ТСХ/ТСЧ) — вход для состава
  популяции симуляции (US4).
- Пул акций «от маркетинга» в виде фикстуры — вход для US6.
- Проектная конституция `.specify/memory/constitution.md` — принципы, которым обязаны
  соответствовать все механики.
- Рабочая спецификация продукта `docs/TZ_X5_gaming_layer.md` — источник контекста и
  зафиксированных решений.
